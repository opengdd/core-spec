A standard for game designers and builders

An OpenGDD package defines what the game must do, and how far the designer's creative control reaches. Everything past that line is the builder's craft.

Designers write it in Markdown and JSON. Builders use it to build the game. The finished build can then be checked against the same package.

The designer

Holds creative control of the design. Writes the rules, tunes the values, sets the direction, and states the acceptance tests.

The builder

Owns the implementation craft. A person, a studio, an AI agent, or any combination; the designer can be the builder too.

Prose, named values, and acceptance tests

Prose describes the game rules, mechanics, and behavior. JSON carries the named values as checkable data. Acceptance tests state what a finished build must demonstrate.

02-mechanics.md

A basic attack lands a critical hit with chance combat.crit_chance. A critical hit deals combat.crit_multiplier times normal damage.

tuning.json

combat.crit_chance 0.05 probability per hit
combat.crit_multiplier 2.0 × normal damage

05-build-plan.md · AT-1

In a seeded run of attacks, criticals occur at the declared chance. Each one deals the declared multiple of normal damage.

This example states one rule in prose, gives each number a name, and makes the required result observable.

Three levels of authority for creative control

Every rule the designer writes carries an authority level. Fixed is the default; Delegated and Personalization must be declared.

Fixed

The build follows the rule as written. A deviation is a defect, not an interpretation.

Criticals occur at exactly the declared chance.

Delegated

The rule sets intent and constraints; the decision within them belongs to the builder.

How a critical hit looks and sounds, within the stated direction.

Personalization

The package declares a question; each build supplies its own answer.

Should a double attack roll the crit chance once or twice?

Validated packages, certified builds

The validator checks the package itself, before any build exists. Certification, an experimental protocol in v0.5, runs the finished build against the package's acceptance tests and records the evidence.

How conformance works

Implementation choices remain with the builder

OpenGDD leaves the engine, renderer, code structure, and other implementation craft to the builder. Two builds can differ in every one of them and both pass certification against the same package.

Another implementation

Version 0.5 is a working draft

The format is being tested against real games and clean-room builds. A clean-room build starts from the package alone, without access to an earlier implementation. Findings that expose a missing rule or weak construct feed into the next revision.
