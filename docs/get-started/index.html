Get started

OpenGDD helps you describe a game clearly enough for someone else to build it. Write the rules and intended experience in Markdown, then use small JSON files for values and lists that benefit from consistent names. Together they form one portable design package, with a clear route from the first rule to the final check. This guide calls the person, team, or AI system making the game the builder.

1Write the game in plain language#

Start by describing the game as you would to a collaborator. Write its rules, behavior, and feel in ordinary prose so the design stays natural to read.

The player moves sideways and can jump to traverse platforms. Touching a spike costs a heart.

These rules live in 02-mechanics.md. Write them as clear instructions for the builder, with each rule stated once. OpenGDD keeps the prose readable while checking the named values and references you add later.

A rule can also describe how something should feel while leaving its implementation open.

At the top of a jump the player hangs for a moment before falling. The rise is quick and the fall is quicker.

The rule names no curve, gravity value, or frame count. It captures the experience and gives the builder room to find an implementation that creates it.

Leaving a detail open is a choice, not a limit. When an exact value matters, give it a name that the prose and data can share.

2Give important values a name#

When a shared gameplay number needs to be read or adjusted as data, give it a tuning key. Use that name wherever the value matters, set it once in tuning.json, and you can change it without searching through the prose.

The player jumps jump.height_tiles tiles from standing. After walking off a ledge, the player may still begin a full jump for jump.coyote_seconds.

tuning.json keeps two kinds of value:

  • a tunable is a value you expect to retune as the game is balanced over time;
  • a constant is a value that helps define the game itself. Changing one is a design change, not a rebalance.
{
  "tunables": {
    "jump.height_tiles": 3.2,
    "jump.coyote_seconds": 0.12
  },
  "constants": {
    "player.hearts": 3
  },
  "meta": {
    "jump.coyote_seconds": { "range": [0.05, 0.2] }
  }
}

You can add a key to the JSON first or use a new name while writing. Like an IDE that tracks names in code, the authoring tool tracks your tuning keys, shows where each one is defined, and offers to add a missing entry to tuning.json. The files remain ordinary Markdown and JSON.

For tunable values, the meta block can add a guardrail. Coyote time, the grace period after a ledge when a jump still works, is currently 0.12 seconds. Its allowed range is 0.05 to 0.2, so the validator reports any later tuning outside those values.

The prose explains what each value does. tuning.json keeps shared gameplay numbers together so they are easy to find, tune, and check. A number belonging to one collection item stays with that item, and a number used only by a test stays with the test.

3Make your first package#

Now bring the design together in five files. This small folder is a complete, portable design document that you can hand to the builder.

platformer/
  manifest.json      the game's identity and reading order
  tuning.json        the named values
  01-overview.md     the fantasy and feel
  02-mechanics.md    the rules
  05-build-plan.md   the route from design to finished game

manifest.json, complete

{
  "opengdd": "0.6",
  "id": "platformer",
  "version": "0.1.0",
  "title": "Platformer",
  "designer": { "name": "You" },
  "target": {
    "platform": "web-2d",
    "genre": "platformer",
    "session_minutes": 20,
    "audience": "anyone who has played a platformer"
  },
  "build": {
    "chapters": ["01-overview.md", "02-mechanics.md"]
  }
}

manifest.json introduces the package: what the game is called, who designed it, who it is for, and what kind of game to build. Choose web-2d or web-3d for the platform. The build.chapters list gives the builder a reading order for your prose.

01-overview.md opens with a fantasy block: one line capturing the player's fantasy, a Feel: line naming the experience to create, and a NOT: line guarding against the wrong direction.

the opening of 01-overview.md

# Platformer

```fantasy
You are a tiny courier crossing a garden of oversized hazards to make one important delivery.
Feel: nimble, readable, determined.
NOT: punishing, cluttered, violent.
```

Everything that follows should serve those few lines.

Put the detailed rules in 02-mechanics.md and their named values in tuning.json. Then use 05-build-plan.md to turn the design into a practical route. Each phase says what to build and how to recognize when it is ready. An acceptance test describes a starting situation, the actions to take, and the results the finished build must show.

05-build-plan.md, complete small plan

# Build plan

## Phase 1: core-loop
Scope: Implement movement, jumping, spikes, and hearts.
Chapters: 02-mechanics.md.
Checkpoint: The player can traverse one test room and take damage.

### AT-1: Jump over a spike
```test
{
  "type": "scenario",
  "given": "a grounded player at full hearts with one spike ahead",
  "when": ["the player performs a full jump", "the player later touches the spike"],
  "then": ["the jump apex reaches jump.height_tiles above its start", "the heart count is one below player.hearts after touching the spike"],
  "diagnostics": ["player-position-timeline", "heart-count-before-after"]
}
```

In plain language: a full jump reaches the specified height, and touching a spike removes exactly one heart.

## Phase 2: content
Scope: Build one short level and give it readable visuals and sound.
Chapters: 01-overview.md and 02-mechanics.md.
Checkpoint: The route is clear, and every important object and action is easy to recognize.

## Phase 3: tune and polish
Scope: Apply the named values, fix defects, and rerun AT-1.
Chapters: 01-overview.md and 02-mechanics.md.
Checkpoint: AT-1 passes and no known blocking defect remains.

Each checkpoint gives its phase a clear finish line. The first phase also has an acceptance test. Its diagnostics name the evidence to return if the test fails.

These five files are already enough to describe a finished game. If you would rather start from files than copy snippets, open the handbook's complete worked package. It has the same five-file shape and passes validation without errors or warnings.

The full OpenGDD format offers optional tools for common design work: collections for lists of content, art direction and palettes for visual intent, and more. Add them when they help your game. The next chapter starts with collections.

4Make lists with collections#

Games are full of lists of similar things: three enemies, fifty cards, or a dozen levels. A collection makes each list easy to grow and browse. Create one folder per list under collections/, then give every item its own JSON file.

platformer/
  manifest.json
  tuning.json
  01-overview.md
  02-mechanics.md
  05-build-plan.md
  collections/
    enemies/
      walker.json       one file per enemy
      flyer.json
      spitter.json

Here, enemies/ is the list and each file is one enemy, which OpenGDD calls a record. Adding another enemy is as simple as adding another file. The folder name becomes the collection id, and each filename becomes a record id. You do not need to repeat the list in manifest.json.

collections/enemies/walker.json

{
  "title": "Walker",
  "speed-tiles-per-second": 2,
  "behavior": "patrols its platform and turns around at the edge"
}

collections/enemies/spitter.json

{
  "title": "Spitter",
  "speed-tiles-per-second": 0,
  "behavior": "stands still and fires along the direction it faces"
}

title is the name the player sees. The filenames walker and spitter are the names the package uses to refer to those enemies, so they must be unique inside enemies/. If you rename a file, the validator points out every reference that needs the new name.

You can mention the whole list or one item directly in your prose:

  • collections.enemies means all enemies;
  • collections.enemies.spitter means the spitter.

a rule in 02-mechanics.md

The final platform introduces `collections.enemies.spitter`.
Only one spitter appears in a level.

That is already a complete collection. Each item can use the fields that make sense for your game. If you want every enemy file to follow the same pattern, the next chapter adds one small schema.

5Keep collection items consistent#

As a list grows, a consistent pattern makes it easier to work with. A collection schema is a small template describing the fields that every item should share. Add one as _collection.json when that consistency helps. Its record section describes one enemy.

collections/enemies/_collection.json

{
  "record": {
    "title": {
      "type": "string",
      "required": true,
      "description": "the name the player sees"
    },
    "speed-tiles-per-second": {
      "type": "number",
      "required": true,
      "description": "how fast the enemy moves; 0 means it never leaves its tile"
    },
    "behavior": {
      "type": "string",
      "required": true,
      "description": "what the enemy does, in plain language"
    }
  }
}

The description beside each field explains what it means. Keeping that explanation here gives the builder one clear place to look, while your prose stays focused on game rules such as when an enemy appears or how it attacks.

The schema also gives you immediate feedback when an enemy file has:

  • a missing required field, such as behavior;
  • a value of the wrong type, such as speed written as text;
  • a field that the schema does not declare.

If the items do not share one useful pattern, leave _collection.json out. Collections with and without a schema are both complete.

This example describes enemy behavior but leaves appearance open. When color, mood, or visual consistency matters, OpenGDD also offers art direction and palette tools.

The schema keeps the list consistent. Your prose brings its items into the game.

6Check and share your package#

When the design is ready, the validator checks that its files, named values, and references fit together. You can then hand the same folder to a builder with a clear route through the work.

  1. Run npx opengdd validate <package-dir>. When working from an OpenGDD source checkout, you can instead run node conformance/validate.mjs <package-dir>.
  2. Work through any errors. Treat each warning as a question worth reviewing; the design may already have an intentional answer.
  3. Send the complete package folder to the builder as a zip archive or Git repository.
  4. Tell the builder to read manifest.json first, implement the phases in 05-build-plan.md, and return the build plus the test evidence that plan requests.
