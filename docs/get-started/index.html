Get started

An OpenGDD package is a game design document made of Markdown and JSON. Prose carries the designer's creative intent. Structured data makes selected claims checkable. Authority levels state who decides. A builder can then implement the game. The finished game can be checked against the same package. The builder may be a person, a studio, an AI agent, or a combination.

1Describe the game in prose#

Every game needs rules, behaviors, and mechanics. In OpenGDD, the designer writes them in ordinary prose. The prose carries creative intent without forcing each sentence into a data structure.

The player moves sideways and can jump to traverse platforms. Touching a spike costs a heart.

Rules live in 02-mechanics.md as ordinary sentences. There is no schema over them, and the builder reads them as ordinary language. These sentences are read, not validated, so keep them consistent, with each rule stated once.

A rule can also decide how something should feel, and leave the method open on purpose.

At the top of a jump the player hangs for a moment before falling. The rise is quick and the fall is quicker.

Nothing there names a curve, a gravity value, or a frame count. It describes what the player feels and leaves the arithmetic to the builder. Two builds of this jump may share no code at all. Both can be faithful, because the rule fixes the feel and leaves the formula open.

Leaving it open is a choice, not a limit. The same jump can be designed precisely, in named values. The next chapter shows how.

2Symbols as value references#

A numeric value written in prose is inconvenient. Finding and changing a number buried in pages of text is hard, and a value typed in two places drifts apart sooner or later. Symbols exist for this reason: a symbol is a named reference to a value, tuned in one place and cited as many times as you need. And unlike prose, it can be validated.

The player jumps jump.height_tiles tiles from standing. And after walking off a ledge, a full jump is still possible for jump.coyote_seconds.

Symbols live in tuning.json and come in two variants. The distinction matters when a build is validated:

  • a tunable is a value you expect to retune as the game is balanced over time;
  • a constant is a value that helps define the game itself. Changing one is a design change, not a rebalance.
{
  "tunables": {
    "jump.height_tiles": 3.2,
    "jump.coyote_seconds": 0.12
  },
  "constants": {
    "player.hearts": 3
  },
  "meta": {
    "jump.coyote_seconds": { "range": [0.05, 0.2] }
  }
}

You can declare a symbol in the JSON, or just mention it while writing: when the authoring tool sees an unknown key in your prose, it offers to create it in tuning.json for you. You stay in your creative flow while inventing symbols, and come back to tune the values later. Nothing forces you to break the flow.

Additionally, meta can carry extra facts about a symbol, like the range a value must always stay inside. Coyote time, the grace period after a ledge where a jump still works, gets 0.05 to 0.2 seconds here, and no further. A range can also grant bounded freedom: the spec may invite each build to pick its own value inside one, and the pick is recorded with the build.

That is the format in miniature. Prose carries the intent, symbols carry the numbers. Freeform where you want it, validated where it counts.

3Collections#

Games repeat themselves: three enemies, fifty cards, a dozen levels. Writing a paragraph for each clogs the prose, and a builder has to guess where the list begins and ends. Collections are handy compartments that group items of one kind.

enemies.json

[
  {
    "enemy_name": "walker",
    "speed_tiles_per_second": 2,
    "behavior": "patrols its platform and turns around at the edge"
  },
  {
    "enemy_name": "flyer",
    "speed_tiles_per_second": 3.5,
    "behavior": "drifts up and down along a fixed vertical path"
  },
  {
    "enemy_name": "spitter",
    "speed_tiles_per_second": 0,
    "behavior": "stands still and fires along the direction it faces"
  }
]

For the collection to be recognized and used by the builder, it needs an entry in manifest.json. The entry defines how to read the collection: this one lives as a single catalog file called enemies.json, and each entry's name sits in the field enemy_name.

the matching entry in manifest.json

{
  "id": "enemies",
  "format": "platformer-enemy-catalog-v1",
  "contract": "03-content.md#the-enemy-catalog",
  "source": { "kind": "catalog", "file": "enemies.json" },
  "authority": { "level": "fixed" },
  "id_member": "enemy_name"
}

format represents the shape you decided this collection has: a name, a speed, a behavior. Give it a version, so a tool can tell one shape from a later one. authority is how much freedom a builder has with these entries. Fixed means none. Delegated lets the builder decide within the stated intent and constraints. Personalization lets the designer ask a question before each build and lets that answer decide. The specification covers all three levels in detail.

The bookkeeping around a collection, that every declared file exists, every name is unique, every reference resolves, is the validator's job to check. It is not yours to memorize.

One field up there is still unexplained: contract. A collection holds the data, but the builder needs to know what it means. That is the next chapter.

4Contracts#

OpenGDD uses contracts to tell builders how to interpret data. A contract is prose that says what the shape of the data means.

A collection is one shape that needs a contract: its fields are yours to invent, and they mean nothing until the contract explains their meaning:

The enemy catalog. Each entry in enemies.json is one kind of enemy. It has an enemy_name, a speed_tiles_per_second, and a behavior. A speed of 0 means the enemy never leaves its starting tile. behavior is what the enemy does, written in plain language.

This contract prose is a section that sits in 03-content.md, exactly where the collection's contract field points. It is where the builder learns about the collection and how to read it.

Notice what it never mentions: how an enemy looks. The spec decides how the game plays; the look of things is left to whoever builds it.

JSON carries the entries, and prose carries their meaning. Symbols use the same pattern: JSON carries each value, and prose gives it meaning.

5The package#

Everything written so far is a handful of loose files. A package makes them one complete, portable design document. A builder can use that document to make the game.

platformer/
  manifest.json      what this is, and what to build from
  tuning.json        the numbers
  01-overview.md     the pitch, and how the game should feel
  02-mechanics.md    the rules
  03-content.md      the enemy contract
  05-build-plan.md   phases, and the tests a build has to pass
  enemies.json       the enemies themselves

manifest.json, complete

{
  "opengdd": "0.5",
  "id": "platformer",
  "version": "0.1.0",
  "title": "Platformer",
  "designer": { "name": "You" },
  "target": {
    "platform": "web-2d",
    "genre": "platformer",
    "session_minutes": 20,
    "audience": "anyone who has played a platformer"
  },
  "build": {
    "chapters": ["01-overview.md", "02-mechanics.md", "03-content.md"],
    "plan": "05-build-plan.md",
    "tuning": "tuning.json"
  },
  "content": [
    {
      "id": "enemies",
      "format": "platformer-enemy-catalog-v1",
      "contract": "03-content.md#the-enemy-catalog",
      "source": { "kind": "catalog", "file": "enemies.json" },
      "authority": { "level": "fixed" },
      "id_member": "enemy_name"
    }
  ]
}

Most of this you have already seen; the content entry is chapter 3's collection, unchanged. The top block is identity: which revision of the format the package is written against, what the game is called, who wrote it, and what it targets. The platform says whether the package targets a 2D or 3D web game. It does not choose the renderer or visual style. This revision accepts web-2d and web-3d. Under build come the chapters, the plan, and the tuning file; the numbered chapters use the format's standard names, from 01 overview through 05 build plan. Some are optional. This small package omits 04-presentation.md, the art direction chapter. That is the whole package. No project file, no build system, nothing to install.

This guide walks a deliberately small slice of the format, and more guides are coming. Until then, the specification continues where this page stops: the manifest, the build plan and its acceptance tests, per-build personalization, and the art direction block.

6Try it#

You have seen the shape of a package: prose for the rules, JSON for the tuned numbers and the lists, a manifest holding them together, and a build plan saying what a finished game must prove. A real package differs from this one mostly in size, plus a few constructs this guide skipped, like per-build personalization.
