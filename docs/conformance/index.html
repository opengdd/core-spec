Conformance

Conformance is what makes "this is an OpenGDD package" a claim anyone can test. Today, the authoring tool checks a package continuously in the browser. A standalone opengdd command is planned, but is not published yet.

The validation engine also lives in the specification repository and runs on plain Node with no dependencies. It reads the package, never runs a game, and reports findings with stable codes, each pointing at the specification section it enforces.

What validation checks

Errors are limited to mechanically testable MUST requirements of the specification:

  • the package envelope: required files present, every declared path inside the package, the manifest valid against its schema;
  • the fantasy block: one fantasy sentence, three to five feel adjectives, non-empty anti-references;
  • tuning: the tunables and constants envelope, finite numbers, declared ranges that contain their own current values;
  • declared expressions and invariants: a closed operator set, resolvable references, finite results;
  • structured content: unique ids, existing contracts, no dangling references where a mechanical target is exposed;
  • acceptance tests: ordered headings, a structured verification descriptor per test, and the fields its class requires.

Warnings flag what deserves a look without breaking validity. A package with zero errors is valid; that word claims a well-formed, internally consistent, honestly declared specification, and nothing more. Validation never judges whether the game is good, and it never runs a build.

The certification chain

A build makes a stronger claim than a package, so it is checked by a longer chain:

  1. The package validates with zero errors.
  2. A builder builds it. Fixed statements bind exactly; Delegated ones are the builder's craft.
  3. The acceptance suite runs. Every acceptance test in the build plan passes, per its own verification descriptor.
  4. A separate audit checks that the tests measure the right thing, that tuned values flow by reference instead of being re-hardcoded, that Fixed rules survive in the implementation itself, and that the builder's disclosed interpretations are honest.
  5. The build ships its manifest (opengdd-build.json): builder, resolved tuning snapshot, acceptance outcomes, and a SHA-256 result hash over a canonical payload. The manifest names what that payload covers, so anyone can recompute the hash and confirm the result they were shown.

The audit ends in one of three verdicts:

certify   certify-with-notes   do-not-certify

In this draft, certified build names the evidence state defined by the public OpenGDD conformance protocol. It does not grant or imply authorization under an OpenGDD certification-mark program. No such program operates today.

Notes distinguish blocking failures from should-fix weaknesses. Any one of these blocks certification outright: a failed acceptance test, a certified runtime value that differs from the resolved snapshot, an incomplete build manifest, an unreproducible result hash. Certification evidence belongs to the build it certifies; it is never written back onto the spec as a promise about future builds.

What is never judged

Honesty about the edges is part of the format:

  • Taste. Certification judges fidelity to the spec, never quality of craft. Two faithful builds of one spec may look and feel different wherever the spec delegates, and both deserve the verdict they earned.
  • Audio. A package may carry an optional audio sub-block, and v0.5 keeps it a draft that creates no certification state: a v0.5 validator and a v0.5 certifier both ignore it, so no audio claim is judged or certified. The fence moves only when the judgment protocol is trustworthy.
  • What a player feels or knows. Claims about experience, belief, or discovery are not state predicates. The format certifies operational witnesses, never the feeling itself; the known limitations page draws this boundary precisely.
