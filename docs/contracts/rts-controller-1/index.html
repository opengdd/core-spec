Controls & camera

RTS controller

rts-controller-1

draft

Make selection, world commands, camera movement, inspection, and cursor feedback explicit.

usually per packageselection compositewide decision surfaceearly

Also touches: Ordering & resolution, World space & grids

Evidence status: Draft-unpublished test artifact. It has not yet completed an external answer-recurrence study.
Explore only. Click choices to understand their consequences. Nothing here changes the contract, saves an answer, or creates a configured download. Use the authoring tool to add a contract to a real spec.
Suggested choices are explanations, not defaults.

What this contract covers

Point, command, watch, read: selection, the smart click, range and reachability, queueing, camera, and inspecting — the decisions every isometric, RTS, or ARPG control scheme has already made, written down once. Parts your game doesn't need switch off by answer.

The mechanism is the loop from pointer input to world command to avatar action, together with the camera that frames it and the inspect channel that reads it. It owns which button carries which verb, what a command means on ground versus on an interactable, what happens when a command cannot be satisfied, whether commands queue, how the camera behaves, and how the player reads objects without acting on them.

It deliberately does NOT own feel: camera stiffness, easing, pathfinding algorithm, cursor art, and animation are the builder's craft. The boundary runs through the middle of the camera: which mode exists and which manual controls exist is convention and lives here; how the follow feels does not.

An interactable is a world object the game declares commandable; the interactables collection carries the classes. A command on an interactable is a request to perform that class's interaction; a command on ground is a request to move. Under a smart mapping one button carries both meanings, resolved by what is under the cursor.

Button roles decide which commands pointer presses request. Acceptance tests that begin with a move or interaction command enter at that command boundary; they do not imply that either pointer button produces the command. This keeps the other command rules explicit even when both pointer buttons carry none.

A rejected command changes no state: no avatar motion, no camera motion, no partial effect. Rejection must be observable to the player; its presentation is craft.

The inspect channel never changes world state. Reading is free, always.

Questions it answers

12 decisions, grouped for reading

Selection

selection-model

What does the player select, and how does selection work?

Choose an option to explore what it means. Nothing will be saved.

Exploring: Permanent single

One hero, always selected. There is no select action at all — every command goes to them. The ARPG way.

Exact wording

Exactly one avatar exists and is always selected. No selection action exists, no selection indicator is required, and no input can deselect. Every world command addresses the avatar.

Exploring: Click single

Click a unit to select it; click empty ground to deselect. A command with nothing selected is refused.

Exact wording

One unit is selected at a time by a selection input on it; a selection input on empty ground deselects. Commands with nothing selected are rejected.

Exploring: Multi group

Drag a box, add to the selection, save numbered control groups. Commands go to the whole selection. The classic RTS way.

Exact wording

Multiple units select via drag-box and additive selection, with numbered control groups up to the group-count knob. Commands address the whole selection.

Why this question matters

A controller with no selection model has no one to command. One always-selected hero is the ARPG convention; groups are the classic RTS one.

Commands and movement

primary-button-role

What does the primary pointer button do when pressed over the world?

Choose an option to explore what it means. Nothing will be saved.

Exploring: Smart

On ground it asks the avatar to move; on an interactable it requests that interaction. The thing under the pointer decides which command is issued.

Exact wording

Over ground, the primary button issues a move command toward the pointer position. Over an interactable, it requests that interaction and issues no move-only command.

Exploring: Move

It always issues a move command. Pressing it on an interactable requests movement there without requesting interaction.

Exact wording

The primary button always issues a move command toward the pointer position. Over an interactable it still moves there and issues no interaction request.

Exploring: Interact

It always requests interaction. On empty ground the request is refused and nothing moves.

Exact wording

Over an interactable, the primary button requests that interaction and issues no move command. Over ground, the press is rejected with observable feedback and changes no world state.

Exploring: None

Over the world it does nothing at all. It may still work inside menus and UI.

Exact wording

Pressed over the world, the primary button changes no state, changes no selection, and issues no command. It may still act inside UI surfaces.

Why this question matters

This answer owns the primary button's world role. It does not judge whether the two buttons together make the game playable, and it does not constrain the button inside UI surfaces.

out-of-range-command

What happens when the player commands an interactable that is too far away?

Choose an option to explore what it means. Nothing will be saved.

Exploring: Not applicable

Nothing has a range: anything can be commanded from anywhere, or interactions happen only through menus.

Exact wording

No interaction has a range: every interactable is commandable from anywhere or interactions happen only through UI. All range templates are pruned.

Exploring: Approach then interact

Click it from across the map: the avatar walks over and does it on arrival. Distance is never a refusal.

Exact wording

The command is accepted from any distance: the avatar paths toward the interactable and performs the interaction on arrival. Distance is never grounds for rejection.

Exploring: Reject out of range

Too far means no: the command is refused with visible feedback and the player must move closer first.

Exact wording

The command is rejected with observable feedback and no state change. The player must move first.

unreachable-destination

What happens when the player clicks somewhere no path can reach?

Choose an option to explore what it means. Nothing will be saved.

Exploring: Nearest reachable point

Click across the river: the avatar walks to the closest spot a path reaches and stops there.

Exact wording

The command is accepted and the avatar travels to the reachable point nearest the target, then stops. Nearest is measured in path distance; ties resolve by the game's declared tie-break.

Exploring: Reject command

The click is refused with visible feedback; the avatar does not move.

Exact wording

The command is rejected with observable feedback and no motion.

Why this question matters

Every pathing game meets an unreachable click; without an answer, two faithful builds diverge on the first blocked dune.

command-queueing

Does a new command replace the current one, or queue behind it?

Choose an option to explore what it means. Nothing will be saved.

Exploring: None replace

A new click wins instantly: the old path is dropped. No queue exists, ever.

Exact wording

A new command replaces the current one immediately: the path is abandoned, no queue exists, and no queued command is ever observable.

Exploring: Bounded queue

Hold the declared modifier to line commands up, capped by the queue-max knob. A plain click clears the line and takes over. The player can see the queue.

Exact wording

A declared modifier input appends commands up to the queue-max knob; an unmodified command clears the queue and replaces. Queue contents are observable to the player.

Exploring: Unbounded queue

Same, with no cap.

Exact wording

A declared modifier input appends commands with no maximum queue length; an unmodified command clears the queue and replaces it. Queue contents are observable to the player.

Why this question matters

Every controller answers this the moment a second click lands mid-travel. The guidance leans on the single-avatar case; queueing is the RTS production convention.

Camera

camera-model

What does the camera do — follow the avatar, or move freely?

Choose an option to explore what it means. Nothing will be saved.

Exploring: Follow locked

Glued dead-center on the avatar (or the middle of the selection), always.

Exact wording

The camera is rigidly centered on the avatar (or selection centroid) at all times.

Exploring: Follow loose

The camera trails the avatar with some give — they never leave the screen, and nothing can detach it. How the trailing feels is the builder's craft.

Exact wording

The camera follows the avatar continuously with craft-defined slack; the avatar never leaves the view, and no input detaches the camera from it.

Exploring: Free camera

The player drives the camera; it follows no one.

Exact wording

The camera is player-driven and does not follow.

Additional context: If you pick this, give manual-camera-pan a real answer — with not-applicable there, nothing can move the camera at all. The machine cannot enforce this; the reviewer does.

Exploring: Free with recenter

Player-driven, plus a declared input that snaps back to the avatar or selection.

Exact wording

The camera is player-driven and does not follow. A declared input recenters it on the avatar or selection.

Why this question matters

Something has to frame the world.

manual-camera-pan

How can the player move the camera by hand?

Choose an option to explore what it means. Nothing will be saved.

Exploring: Not applicable

No manual camera at all — it is fully automatic. Only coherent with the follow modes.

Exact wording

No manual pan: the camera is fully automatic and no input moves it. Coherent only with the follow modes.

Exploring: Edge scroll

Push the pointer to the screen edge and the camera pans.

Exact wording

The pointer at the view edge pans the camera.

Exploring: Drag pan

Hold a declared button and drag the world.

Exact wording

A declared button drags the camera.

Exploring: Keys

Declared keys pan the camera — WASD, arrows, whatever the game names.

Exact wording

Declared keys pan the camera.

Exploring: Combined

Two or more of the above, listed in your game's prose.

Exact wording

Two or more of the above, enumerated in game prose.

Inspecting objects

inspect-channel

How does the player read a world object without acting on it?

Choose an option to explore what it means. Nothing will be saved.

Exploring: Not applicable

No per-object readout exists in this game.

Exact wording

No inspect channel: the world offers no per-object readout. All inspect templates are pruned.

Exploring: Hover tooltip

Rest the pointer on a thing and its readout appears right there — no click, and nothing in the world changes.

Exact wording

Resting the pointer on an object shows its readout in place, with no click and no world-state change. Staging per inspect-staging.

Exploring: Click inspect

A declared input opens the object's readout in a declared panel. That input does nothing else.

Exact wording

A declared input on an object opens its readout in a declared surface. The input carries no other verb.

Exploring: Dedicated mode

A toggle enters inspect mode: pointing reads instead of commanding.

Exact wording

A declared toggle enters an inspect mode in which pointing reads instead of commanding.

Explore the choices

inspect-staging

Does the hover readout arrive all at once, or in stages?

Applies when Inspect channel is Hover tooltip.

Choose an option to explore what it means. Nothing will be saved.

Exploring: Single stage

Everything appears at once on hover.

Exact wording

The full readout appears on hover at once.

Exploring: Two stage

Name and the key live number appear instantly; stats and flavor arrive after the stage2-delay-ms dwell. Live values tick in both stages.

Exact wording

A compact stage (name and the key live value) appears immediately; the full stage (stats, flavor) appears after the stage2-delay-ms knob of continuous hover. Live values tick in both stages.

Why this question matters

Staging is a property of hover, so this question is only asked when the inspect channel is hover — otherwise it is pruned, unasked.

Cursor feedback

cursor-context

Does the cursor change to show what a click here would do?

Choose an option to explore what it means. Nothing will be saved.

Exploring: Static cursor

One cursor everywhere; the game signals what things do some other way.

Exact wording

One cursor everywhere; affordances are communicated by other means.

Exploring: Context cursor

The cursor changes over each interactable class — each row declares its form — and over plain ground shows the ground form your game's prose declares.

Exact wording

The cursor's form follows what is under it, per the cursor member of the interactables collection. Over plain ground it takes a ground form the game MUST declare in its own prose; an undeclared ground form is the scope-by-implication this option forbids.

Why this question matters

Even a never-changing cursor is a decision.

Explore the choices

cursor-magnetism

Does a click just beside an interactable still count as hitting it?

Choose an option to explore what it means. Nothing will be saved.

Exploring: None

What you see is what you hit: a click beside a crate is a ground click.

Exact wording

Hitboxes match visual bounds; a click beside an interactable is a ground command.

Exploring: Snap radius

A click within the magnetism-radius-px of something interactable snaps to it — nearest wins. Ground clicks need clear space.

Exact wording

A pointer within the magnetism-radius-px knob of an interactable's bounds resolves to that interactable, nearest-first; ties resolve by the game's declared tie-break. Ground commands require clearing the radius.

Why this question matters

Two builds that disagree here disagree on every near-miss click.

Collections

interactables

Interactables

The classes of commandable world objects; the game declares the rows, and this core fixes only their shape. An empty collection is legal: the controller is then movement, camera, and inspect alone.

FieldKindWhen it appearsMeaning
id string Required Stable class name; the id command and diagnostic events carry.
interaction citation Required Citation to the package prose section that defines what interacting with this class does. The contract routes the command; the game owns the meaning.
cursor string Applies when Cursor context is Context cursor. The cursor form shown over this class, a kebab-case name the game owns — cursor art is craft, so the contract requires the declaration, never the vocabulary. MUST be present exactly when cursor-context is context-cursor and absent otherwise.

magnetism-resolves-near-miss

a near-miss inside the snap radius resolves to the interactable

scenarioonce

Applies when Cursor magnetism is Snap radius.

A near-miss inside the radius named by Knob cite magnetism radius px snaps to the interactable; beyond it, the ground receives the command; among candidates the nearest wins.

Test steps and diagnostics
Given

a pointer position outside an interactable's visual bounds but within the distance named by Knob cite magnetism radius px, and a second position just beyond that distance

When
  • command target resolution is evaluated at each pointer position
Then
  • the within-radius position resolves to the interactable
  • the beyond-radius position resolves to ground
  • with two interactables in radius the nearer wins, ties per the game's declared tie-break
Diagnostics
  • cursor-target-resolution
  • distance-computed
