How the format evolves

OpenGDD is on a 0.x workbench. Minor versions may reshape constructs while the format earns its stability against real games. Every construct in the current draft is there because two different games needed it. The changelog records each version's migration path. Schema URLs are versioned and never repurposed, so a package that validated under its own version will always validate under it.

The 1.0 promise

Version 1.0 is a set of criteria. There is no target date. When all five hold, 1.0 is declared:

  1. Stability. Once a package is valid, it stays valid. Later 1.x releases will not break it. Breaking changes wait for version 2.0, and they are announced well before they arrive.
  2. Testable conformance. A suite of checks decides whether a package conforms. Anyone who runs it gets the same answer.
  3. An independent implementation. Someone outside the project has built a working tool from the written specification alone. That is the proof the specification is complete.
  4. Public review. A public review round has run, and every finding is resolved.
  5. The battery. The format is tested against real games, and it must express them at the predicted level. The known limitations page must be current.

Until then the version stays at 0.x: the format still changes as real games teach it.

How proposals happen

Evidence first. A construct enters the specification when real games need it, not when an argument sounds right. The strongest proposal names a game, shows what the current format forces it to do awkwardly or dishonestly, and sketches the smallest construct that fixes it. Two independent instances of a need move a proposal from "interesting" to "ready to draft."

Proposals go to GitHub Discussions on the specification repository: new constructs in Proposals, questions in Q&A, and things you built in Show and tell. Security reports go to security@opengdd.org, never to public threads.

Open questions, right now

Questions the current draft has open, where opinions and evidence are wanted:

  • A designer shorthand for acceptance tests. Writing formal verification descriptors is the steepest part of authoring a package. Should there be a shorthand tier that a tool can expand into the formal descriptor?
  • Prose sub-files for large specs. Chapters grow. Should a chapter be able to split into paired record-and-prose sub-files without inventing a second structure?
  • The level-encoding family. The current grid encoding handles parallel string layers. Single-grid pictures and overlapping glyphs recur in real games. What does the family need?
  • The solver interface. Authored puzzles can declare solvability, but the contract an independent solver would certify against is still open. The evidence so far says the drafted shape must widen before it locks.
  • The 3D capture recipe. A web-3d build can certify today when its acceptance tests need only logic and state observations. A rendered-capture profile needs a renderer-neutral way to classify what sits under a sampled pixel; the recipe is unwritten.
