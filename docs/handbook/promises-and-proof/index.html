Promises and proof

Applies to every package.

Package checking checks the paper: its names, links, rules, and prose. Record checking compares the builder's report with the package. Audit checking judges whether the finished build is faithful and whether the intended feel holds.

Validation of source files is not proof that the finished game works. A build record is the JSON report from the builder, the person, team, studio, AI system, or combination that turns the package into a game. It says what was built and which tests the builder reports as passed.

a validator finding, from the command line

ERROR [PROSE_CITATION_DANGLING] 02-mechanics.md:3 — prose citation `stamina.regen` does not resolve to a tuning.json key (SPEC §4)

Quote the bracketed code when asking for help; it names the exact rule the validator applied.

You meet three kinds of checking:

  • Package checking asks whether the source package is internally consistent. The validator checks files, data, and references; a human reviews the prose.
  • Record checking compares the build report with the source package and checks that the report agrees with itself. It does not rerun tests or prove that the builder's claims are true.
  • Audit checking runs tests and reviews art direction against the finished game. A separate auditor performs it when certification is sought. No audit is required for package or build-record validity; without one, those files may validate while the finished game remains unaudited. A runner is the tool or person that executes the tests; the build record names it; its published description, the runner profile, says how it samples or walks the scope. The experimental audit profile describes capture, evidence, and judged review. Both profiles belong to the experimental certification protocol.

Two severities, only two:

  • An error means the spec or build does not meet the format's rules.
  • A warning points at something worth reviewing but does not make the package invalid.

The authoring tool reports package errors while you write, so missing names and invalid data can be corrected before a build begins.

Full rules: OpenGDD specification, §2d.
