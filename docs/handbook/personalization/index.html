13. Personalization

Your design can ask questions. One spec, and each build answers before it is made: one game, several honest shapes of it. You write the question, the options, and what each option does to the numbers.

personalization.json, the questions file

{
  "questions": [
    {
      "id": "wave_pressure",
      "prompt": "How hard should the waves press?",
      "type": "choice",
      "default": "steady",
      "affects": ["tuning.json", "04-presentation.md"],
      "options": [
        {
          "id": "calm",
          "label": "Room to think",
          "notes": "Between waves the field goes quiet and the music drops out.",
          "tuning_overrides": { "wave.gap_seconds": 24 }
        },
        {
          "id": "steady",
          "label": "Steady pressure",
          "notes": "The pacing as shipped."
        },
        {
          "id": "relentless",
          "label": "No breathing room",
          "notes": "The horn for the next wave sounds while the last one is still on the field.",
          "tuning_overrides": { "wave.gap_seconds": 9 }
        }
      ]
    }
  ]
}

One question, three answers a build can give. Its members:

  • id: the question's name in the package, and what a build records.
  • prompt: the question as the builder is asked it.
  • options: the whole answer space. An id outside this list fails validation.
  • default: the answer that applies when the question is skipped, naming one declared option.
  • tuning_overrides: the tunable values an option overrides, here the seconds between waves.
  • affects: the files you are telling the builder this answer reaches.

Every question carries a default, so a build that answers nothing is still a whole game, tuned the way you shipped it.

What an answer moves by machine is numbers, through tuning keys. Everything else it changes, like the horn sounding early, lives in prose the builder reads: the notes here, and the chapter sections the question governs. Give a decision a number and a tuning key when you want it checked.

Not here: choices a player makes while playing. A difficulty toggle in a menu, or a boon taken mid run, belongs to the running game.

The authority chapter's > PERSONALIZATION: tag names one of these ids, marking where in your prose a question rules. A number question resolves an answer straight into a tunable's range: the tuning chapter's bounded freedom, now being asked.

Every build records the answers it was given. That a default names a declared option, and that an override lands inside its key's range, is the validator's job, not yours.
