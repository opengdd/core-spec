Preflight checklist

Use before handoff.

The validator checks what it can prove from files. A final human read checks the part only a designer can see: whether the package says one clear, coherent thing. Use this list before you hand the design to a builder.

The package opens cleanly#

  • Run npx opengdd validate <package-dir> and resolve every error.
  • Review each warning. Fix accidental omissions and confirm intentional ones.
  • Confirm the five required files are present and every chapter named by manifest.json exists.

The design reads as one game#

  • Read the fantasy block, then skim every chapter against it. The rules, mood, and presentation should describe the same experience.
  • Check that each rule is stated once and each shared tuning value is cited by its key instead of copied into prose. Keep item-specific numbers in their collection records and test inputs with their tests.
  • Look at player-visible differences that change play. Define each one in the prose or through Personalization. Leave choices to the builder only when their limits are clear.

Opt-in files are connected#

  • Make sure every collection is referenced in prose or by another declared mechanism. Add _collection.json only when its records benefit from one shared schema.
  • For a graph, confirm the declared links are the ones the game needs. Add a document-check acceptance test when the graph must also obey a rule such as never looping.
  • For direction and palettes, keep judged intent distinct from measured constraints, and connect every measured constraint to an acceptance test.
  • For Personalization, make every default meaningful and read each answer as a complete version of the same game.
  • For a contract, read the adopted core, answer every applicable question, and regenerate its build-plan tests after an answer changes.

The build plan is complete#

  • Follow the phases in 05-build-plan.md in order. Each phase should say what to build, which chapters define it, and how to recognize completion.
  • Read every acceptance test beside its plain-language restatement. Together they should cover the promises that matter most, without prescribing the builder's code or engine.

Use the OpenGDD specification when this review finds a format question. Update the package when it finds an unresolved design decision.
