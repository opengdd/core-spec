Seeds & determinism

Opt-in: add this when your game needs it.

A seed is a text value used to reproduce random results. A seed address is an address for a repeatable random sequence. It includes locations and a stream name so different parts of the game use separate sequences.

03-content.md, where the floor generator is described

Every floor draws its layout from the seed address {seed}:floor:{n}:stream:layout. Here n counts floors from 1 at the entrance and never goes negative, and the stream's draws are consumed in room order, outward from the stairs.

{seed} stands for the seed used for this run, and {n} stands for the floor number. A draw is one request for the next random value in the sequence.

The format fixes the random algorithm. The same seed and seed address, used by the same Fixed procedure, produce the same sequence in every build. The OpenGDD specification defines the algorithm; your chapter defines what each seed address means.

For each seed address, state:

  • what labels such as floor and layout mean;
  • what each number counts, and whether counting starts at 0 or 1;
  • whether coordinates may use negative numbers;
  • which game events request draws, and in what order.

These declarations stay in your prose. There is no separate JSON file for them.

When an acceptance test uses seeds, list them in that test. A runner is the tool or person that executes the tests. The build record, the builder's JSON report of what was built, names it. Its published description, the experimental runner profile, states how it samples or walks the test's scope and how many cases it checks for each seed.

If the generating procedure is Delegated, different builds may produce different results. Keep it Fixed when every build must reproduce the same world.

Full rules: OpenGDD specification, §§2a, 6.
