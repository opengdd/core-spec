Runtime state

Opt-in: add this when your game needs it.

Some design rules need to name a value that changes during play, such as oxygen left, the current score, or progress toward an objective. Runtime state gives that changing value a stable name.

02-mechanics.md, naming the diver's oxygen

The oxygen left right now is state:number:oxygen_seconds. Read it after each full second spent diving and immediately after anything restores it.

The state:number: prefix says this is a changing numeric value, not a number from tuning.json. Its value might be 47 now and 46 one second later.

Writing the name in one of the package's main prose chapters declares it. The surrounding prose explains what the value means and when it should be read. Prose and acceptance tests can then use the same name without depending on a particular engine or code structure.

The name does not create the value, update it, or tell the builder how to store it. Your mechanics define how it changes, and the builder chooses the implementation.

OpenGDD also has a less common state:member:<set>:<member> form for a yes-or-no question about membership in a declared runtime set. Use it only when another OpenGDD mechanism declares that set. Writing the name alone does not create one.

Full rules: OpenGDD specification, §4a.
