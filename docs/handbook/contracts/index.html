Contracts

Opt-in: add this when your game needs it.

A contract brings a proven game mechanic into your design: a health bar, a backpack, a crafting recipe. It is a ready-made list of the decisions behind that mechanic — decisions thousands of games have made before yours, each in its own way. You answer them once, on purpose, instead of finding them later as bugs.

Pick a contract definition and copy it into your package. Answer its questions, then write the values, rows, and verification inputs it asks for. A public catalogue of ready contracts opens with a later release; a contract file from any source works the same way today.

You can also use a contract as a checklist, without copying any file: read each question, settle the answer in your design prose, and stop there. This gives you the decisions without the structured form and its named tests.

Your copy of a contract, with your answers, is an adoption. One contract serves many adoptions, and every adoption answers the same set of questions. Health and stamina are both Ranged value adoptions; they answer some questions differently, so they behave differently. The same holds for every contract: a backpack and a store are both Container adoptions, each with its own answers and numbers.

contracts/stamina.json, an excerpt from one filled adoption

{
  "contract": "ranged-value",
  "version": 1,
  …
  "questions": {
    "at-min-effect": {
      "asks": "When a loss would drag the value below min, what happens?",
      …
      "options": {
        "clamp": {
          "meaning": "The value stops at min. The overkill is thrown away. Nothing is told about it, and nothing else happens.",
          "semantics": "The value saturates at min. The excess is discarded, reported to no one, and carries no further consequence from this contract; the event otherwise applies in full."
        },
        …
        "unbounded": {
          "meaning": "No floor. The value keeps falling below min, and your rules may read how far it went.",
          "semantics": "min does not constrain the value downward: the delta applies in full and the result is stored, even below min, where game rules may read it. min stays declared and citable, and thresholds at or above it are tested normally."
        }
      }
    },
    …
    "insufficient-cost": {
      "asks": "When something tries to spend more than the pool has left above min, what happens?",
      …
      "options": {
        "reject-action": {
          "meaning": "Can't afford it, can't do it. The action is refused and nothing is deducted.",
          "semantics": "The spend is rejected and the action it would have paid for does not occur. The value is unchanged and no threshold fires."
        },
        "partial-spend": {
          "meaning": "The pool empties to min and reports how much it actually got. What a partly-paid action does is your call.",
          "semantics": "The value is set to min and the spend reports the amount actually spent: the headroom above min before the spend. What the action does with a partial spend is game prose; the contract fixes only the end state and the reported amount."
        },
        …
      }
    }
  },
  "declares": {
    "values": {
      "min": { "description": "The pool's floor. Moving the floor changes the mechanism, not just its balance. Declared even when at-min-effect is unbounded, where it is a landmark." },
      "max": { "description": "The pool's ceiling. Pool size is a common number to change during a balance pass. Declared even when at-max-effect is unbounded, where it is a landmark." },
      "initial": { "description": "The value the pool holds at the start of a run." }
    }
  },
  …
  "answers": {
    "at-min-effect": "clamp",
    "insufficient-cost": "reject-action"
  },
  "values": {
    "min": 0,
    "max": 100,
    "initial": 100
  },
  "rows": {
    "thresholds": [
      {
        "id": "exhausted",
        "value": 0,
        "direction": "falling",
        "refire": "once",
        "rearm": "run-reset"
      }
    ]
  }
}

Every option has a meaning sentence: the promise you make as the designer. Some options add semantics, a more precise sentence that binds the builder and the acceptance tests.

The copied part above answers is the definition, the blank form. The two … lines hide the rest of the definition: more questions, value names, numeric rules, and the pack hash. The visible declares.values block shows the three number names this adoption must fill.

When two adoptions use one definition, the validator compares their copied definitions after parsing the JSON. Reformatting is safe; reordering members is not, so preserve the definition's member order.

In your filled adoption, you write answers, values, any rows, and any requested verification inputs below the definition. Some questions only apply after another answer; the file says which, and the validator does not ask for the rest.

The filename is the address that prose cites. contracts.stamina names this adoption and contracts.stamina.max names its max value. Renaming the file renames those addresses, and the validator reports every citation left dangling.

The validator checks that every asked question has an answer, each value is inside its declared range, every row has the declared fields, and all numeric rules hold. In the example, exhausted fires once and re-arms at run reset. The common bug this prevents: a warning that fires again on every crossing while the pool sits at zero.

Without its pack file, the adoption is promised: it binds the builder the same way Fixed chapter prose does. An audit — a review of the finished game — judges whether the build kept it. To make the adoption checked, put ranged-value-1.pack.json next to it and copy the hash from the contract's catalogue page into the adoption's pack field. The catalogue page prints this SHA-256 fingerprint beside the pack download.

Some tests in a pack ask you where they apply. A general-test template names that designer-supplied scope through inputs:scope:

{
  …
  "inputs": { "scope": {} },
  "test": {
    "type": "general",
    "scope": "{{inputs:scope}}",
    "holds": "the threshold behavior matches the answered contract"
  }
}

Checked answers become named acceptance tests the build must pass. If the build behaves differently, it fails the test by name. Run npx opengdd render-contract-tests <package-dir> to print the named tests again after an answer changes. The command prints a read-only view; do not paste it into 05-build-plan.md. For this row, the rendered test includes:

### AT stamina/threshold-fires-once/exhausted — exhausted fires once, then waits to re-arm
"then": ["the exhausted crossing is reported exactly once over the whole sequence, on the first qualifying crossing"]

A contract records decisions and tests. It does not choose how the builder implements the mechanism, and package validation does not run the finished game.

A public catalogue of ready contract definitions opens with a later release. Until then, any contract definition file you hold works the same way: copy it into your package and answer it.
