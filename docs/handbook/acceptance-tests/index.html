Acceptance tests

Required: every spec has this.

An acceptance test turns an important design promise into something the builder, the person, team, studio, AI system, or combination that turns your package into a game, can demonstrate. A test is a heading followed by one structured block. The block sits directly under the AT-n heading; put any context prose after it. Its fence carries the tag word test; that word tells tools this block is a test. Place it beside the build-plan stage it belongs to.

05-build-plan.md, under AT-4: Alarm on sight. AT-4 is this test's permanent number.

{
  "type": "scenario",
  "given": "a guard on patrol with the player inside its view cone",
  "when": "the player stays visible for alarm.spot_seconds",
  "then": ["the guard raises the alarm", "every other guard on the floor starts searching"],
  "diagnostics": ["visibility-timeline", "guard-state-after"]
}

This is a scenario because it describes one situation. given is the starting situation, when is what happens, and then lists the required results. Each may be one string or a list of strings. diagnostics names the evidence a runner, the tool or person that executes the tests, should produce.

Use a scenario, unless the promise is about many cases.

A general test states a promise across a scope. scope describes the cases in designer words, and holds says what must be true across them. seeds names repeatable random sequences that generate cases, so the builder can reproduce a failure.

05-build-plan.md, checking the generated floors of Emberdeep

{
  "type": "general",
  "scope": "first floors generated at default tuning",
  "holds": "every floor satisfies every Fixed generation constraint in 02-mechanics.md",
  "seeds": ["emberdeep-at-12"],
  "diagnostics": ["sample-seed", "layout", "failed-constraint"]
}

The runner's published description says how it samples or walks a general test's scope, for each seed when seeds are present. A build record is the builder's JSON report of what was built. It says which general tests were sampled instead of checked across their whole scope. A whole-scope result can prove an absence, a minimum, or a promise about every case; a sample cannot.

Dotted names inside test sentences, such as alarm.spot_seconds, are instructions for the runner. The package validator does not resolve that prose as a citation. The test states the required result, not the implementation, so different runners may demonstrate the same result.

Full rules: OpenGDD specification, §6.
