Acceptance tests

Required: every spec has this.

An acceptance test turns an important design promise into something a builder can demonstrate. You place each numbered test beside the build-plan phase it belongs to.

05-build-plan.md, under the heading AT-4: Alarm on sight

{
  "type": "scenario",
  "given": "a guard on patrol with the player inside its view cone",
  "when": "the player stays visible for alarm.spot_seconds",
  "then": ["the guard raises the alarm", "every other guard on the floor starts searching"],
  "diagnostics": ["visibility-timeline", "guard-state-after"]
}

In the Markdown file, open this block with three backticks followed by test. That label marks the block as a check. Restate the same check below it in plain language for readers who do not run tests.

In plain language: if the player stays in one guard's view cone for the spotting time, that guard raises the alarm and every other guard on the floor starts searching.

The fields describe the check:

  • type is scenario because this test describes one situation. The OpenGDD specification defines broader test types for other kinds of proof.
  • given: the situation the check starts in.
  • when: what happens. One string, or a list when the check takes several steps.
  • then: the required results.
  • diagnostics: the information reported when the test fails.

Most moment-to-moment behavior uses a scenario. Use a broader test type only when the rule itself is broader, such as requiring every generated level to remain winnable.

The test states the required result, not the implementation. A person, an engine-specific testing tool, or an AI builder may run the check differently and still demonstrate the same result.

Full rules: OpenGDD specification, §6.
