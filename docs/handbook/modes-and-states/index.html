8. Modes & states

Time does not flow the same everywhere in your game: it runs during a dive, holds still while you plot the course. A mode is a named stretch of play, told apart by which clocks run inside it. Name your modes, and every later rule can say when it applies.

tuning.json, one field beside the numbers

{
  "clocks": {
    "modes": ["dive", "plotting"],
    "clocks": {
      "dive_clock": {
        "unit": "seconds",
        "governs": ["state:number:oxygen_seconds"],
        "behavior": {
          "dive": "advances",
          "plotting": "frozen"
        }
      }
    }
  }
}

A clock is one source of advance, such as running time or a turn index. Each clock states what it does in every declared mode, from a closed set of four:

  • advances or frozen: the clock runs, or it holds still.
  • discrete-only: it moves in steps, like a turn index.
  • does-not-exist: no value in that mode at all; missing, not zero.

The governs line names a quantity the game keeps while running. A tuning key sits bare in your prose, as the identifiers chapter showed; a state name wears state: in front, because it points at the running game and not at a file. Your prose says what it is:

02-mechanics.md, where the quantity gets its meaning

state:number:oxygen_seconds is the breathable air left in the hull, and it stops draining the moment the boat surfaces.

Not here: a difficulty setting, a menu screen, a chapter of the story. A mode is about how time moves, not a label for a part of your game. Exactly one is active at a time, and modes never nest: a situation inside a situation, such as a held breath partway through a dive, becomes a mode of its own, and every clock then states its behavior there too.

Every clock covers every mode, and checking that is the validator's job, not yours.
