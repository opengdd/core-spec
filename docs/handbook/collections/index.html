Collections

Opt-in: add this when your game needs it.

Games are full of lists: technologies, recipes, cards, levels. A collection keeps one kind of content in one folder, with one JSON file per item.

collections/, at the package root

collections/
  technologies/
    fire-making.json
    kiln-building.json
    stone-tools.json
  recipes/
    recipe-charcoal.json
  items/
    charcoal.json

Each folder under collections/ is one collection. The folder name is its id, and each filename is a record id. The folders are the declaration, so there is no collection list to maintain in manifest.json.

collections/technologies/kiln-building.json, one record

{
  "title": "Kiln Building",
  "era_order": 2,
  "note": "Fire held in a shape, instead of loose on the ground."
}

The fields are yours. title is what the game displays; kiln-building is the record id the package refers to. In prose:

  • collections.technologies means the whole collection;
  • collections.technologies.kiln-building means this record.

If you rename a record, the validator points to every reference that still uses the old id.

Records may use whatever fields they need. When every record should use the same fields, add the optional schema file.

collections/levels/_collection.json

{
  "record": {
    "title": {
      "type": "string",
      "required": true,
      "description": "the level name shown in the level list"
    },
    "campaign-order": {
      "type": "integer",
      "required": true,
      "unique": true,
      "description": "the level's place in the campaign, counting from 1"
    }
  }
}

Each description explains how to use the field. The schema reports missing fields, wrong value types, unexpected fields, and duplicate values marked unique.

A field can point at another record. The Links chapter shows the link field type and its checks.

Leave _collection.json out when the records do not need the same required fields. Both forms are complete collections.

Full rules: OpenGDD specification, §1b.
