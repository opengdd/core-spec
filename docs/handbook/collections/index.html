6. Collections

Games repeat themselves: three enemies, fifty cards, a dozen crops. The format gives that repetition a home. A collection keeps entries of one kind together in one catalog file.

crops.json, the catalog file

[
  {
    "crop_id": "millet",
    "days_to_ripen": 3,
    "after_harvest": "regrows on its own and can be cut again"
  },
  {
    "crop_id": "pumpkin",
    "days_to_ripen": 8,
    "after_harvest": "clears the plot and leaves it bare"
  },
  {
    "crop_id": "clover",
    "days_to_ripen": 2,
    "after_harvest": "stays in the ground and feeds whatever is planted next"
  }
]

the matching entry in manifest.json

{
  "id": "crops",
  "format": "farm-crop-catalog-v1",
  "defined_in": "03-content.md#the-crop-catalog",
  "source": { "type": "catalog", "file": "crops.json" },
  "authority": { "level": "fixed" },
  "id_field": "crop_id"
}

The catalog's fields are yours to invent. The manifest entry tells everyone how to read them:

  • id: the collection's name in the package.
  • format: the shape you decided these entries have, versioned so a tool can tell one shape from a later one.
  • defined_in: the section of your own prose that says what the fields mean: what days_to_ripen counts, and that after_harvest is plain language for the builder.
  • source: one catalog file called crops.json, holding every entry.
  • authority: how much freedom a builder has with the entries; the levels are the authority chapter's subject.
  • id_field: the field that names an entry, here crop_id.

JSON carries the entries, and prose carries their meaning.

Notice what an entry never mentions: how a crop looks. The spec decides how the game plays, and the look of things is left to whoever builds it. Directing that look, where you want it directed, is the direction chapter's subject.

The bookkeeping around a collection, that every declared file exists, every name is unique, every reference resolves, is the validator's job to check. It is not yours to memorize.
