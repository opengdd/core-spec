Tuning

Required: every spec has this file. ranges and rules are optional inside it.

One file holds the shared numbers a build reads. A range says how far a number may move, with both ends included. A rule is a line of arithmetic about those numbers that must stay true whenever they change. The validator checks each rule and reports when it is false. A rule never changes a number.

tuning.json, the numbers file

{
  "values": {
    "dash.speed_tiles_per_second": 12,
    "dash.duration_seconds": 0.15,
    "dash.cooldown_seconds": 0.6,
    "gap.width_tiles": 1,
    "level.width_tiles": 24,
    "room.width_tiles": 8
  },
  "ranges": {
    "dash.speed_tiles_per_second": [8, 20],
    "dash.duration_seconds": [0.1, 0.3],
    "dash.cooldown_seconds": [0.3, 1.5]
  },
  "rules": {
    "no-dash-while-dashing": "dash.cooldown_seconds >= dash.duration_seconds",
    "dash-covers-the-gap": "dash.speed_tiles_per_second * dash.duration_seconds >= gap.width_tiles"
  }
}

values gives each shared gameplay number one name and one current value. Each key has two or more segments joined by dots. Both underscores and hyphens are legal inside a segment; underscores are the usual spelling.

Seventeen first words belong to other parts of OpenGDD and cannot begin a tuning key: pillars, mood, anti, must_keep, colors, contrast, timing, values, ranges, rules, runtime, clocks, manifest, build, contracts, palette, and collections. Start your keys with anything else. No segment anywhere in a key may be json or md.

ranges says how far a value may be moved later: by you when balancing, or by the builder when the design allows it. A value without a range stays fixed as written.

rules holds the relationships between values. Each rule has a name, made of lowercase words joined by hyphens, and one line. no-dash-while-dashing keeps the cooldown at least as long as the dash, so one dash ends before the next can start. dash-covers-the-gap makes sure a dash always crosses the gap.

A rule is one comparison between two sums. Use one of == != < <= > >=, with plain numbers and keys from values combined by + - * /. A rule reads keys from values only; a collection record's number or a runtime value cannot appear in one. The functions are min, max, and floor. floor rounds down, which is useful for a whole-number count:

tuning.json, a whole-number rule using values declared above

{
  "two-rooms-fit-across": "floor((level.width_tiles - 2) / room.width_tiles) >= 2"
}

Multiplication and division happen before addition and subtraction; the parentheses above subtract the two wall tiles first. Use parentheses when unsure.

Suppose a balance pass sets the speed to 8 and the duration to 0.1. Both are inside their ranges, and dash-covers-the-gap still fails:

rule "dash-covers-the-gap" does not hold
  dash.speed_tiles_per_second * dash.duration_seconds >= gap.width_tiles
  8 * 0.1 = 0.8, which is not >= gap.width_tiles = 1

The validator names the rule, shows the rule as you wrote it, and shows the numbers that made it false. A false rule is an error: the package does not validate until the rule holds.

Rules are about the numbers written in the design. "The player never has more than three dashes stored" is about what happens during play, so it is an acceptance test, not a rule.

A number that belongs to one collection item stays in that item's record. A number used only by a test stays with the test.

Full rules: OpenGDD specification, §4.
