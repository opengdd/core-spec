Runtime values

Opt-in: add this when your game needs it.

Some design rules need to name a value that changes during play, such as oxygen left, the current score, or progress toward an objective. A runtime value gives that changing value one stable name. Its address, the complete dotted name used to point at it, always starts with runtime..

02-mechanics.md, naming the diver's oxygen

The oxygen left right now is runtime.oxygen_seconds. Read it after each full second spent diving and immediately after anything restores it.

A numbered chapter is a file named NN-name.md. Writing the name is the whole declaration; there is no separate list. It then becomes usable in every chapter, in clocks.json, and in tests. The sentence around the name says what the value means and when it is read.

An undeclared name produces RUNTIME_UNDECLARED; the validator tells you to declare it by writing it in a chapter with a sentence saying what it is, or by naming it in a clock's advances. A misspelling that was itself written in a chapter is not caught, because that writing declares a second value. Before handoff, read the chapters' runtime names once so near-duplicates do not survive review.

The name does not create, store, or update the value. Your mechanics define how it changes. The builder, the person, team, or system that turns your package into a game, chooses the implementation.

Acceptance tests can name the same address. A clock that names the value in advances also counts as declaring it. The Modes & clocks chapter explains that optional timing table.

Full rules: OpenGDD specification, §4b, Runtime values, time modes, and clocks.
